# Phase 9, Plan 02: Before/after proposal change + demo queries [throwaway]

## Phase Goal

ROADMAP `**Goal:**` (verbatim): A self-hosted Graphiti/Neo4j service demonstrably changes a proposal after learning a preference.

MVP note: as recorded in 09-01, the ROADMAP Goal line is not in "As a / I want to / so that" form and no story is invented here. `/gsd mvp-phase 9` would convert it. The plan shape does not depend on it.

<objective>
Deliver STR-03: the same scheduling input visibly produces a different, better proposal after one preference fact is ingested, with the graph shown before and after in Neo4j Browser using a query from `graph/queries.cypher` (D-14, D-15).

09-01 proved the service round trip on group_id `tracer`, deliberately leaving demo user A's partition empty so this plan has a real before state. This plan adds three things to THIS repo and nothing else:
- `graph/queries.cypher` — the paste-ready Browser queries, including the one per-user query run identically before and after.
- `lib/agent/graph-preferences.ts` — `fetchGraphPreferences(userId)`, the fails-closed HTTP read.
- ONE additive call site in `lib/agent/**` where a learned `default_meeting_duration` overrides the platform default duration.

**No Postgres write-back (D-17, deliberately simplified).** The app calls the graph service's `GET /preferences` directly at proposal time. Nothing in this plan writes back to Postgres `Preference` rows. A sync job is new plumbing the 60-90 minute budget cannot afford, and nothing in STR-01..03 needs the Postgres hop (09-RESEARCH "Orchestrator Review Corrections" item 5). Consequence: `prisma/schema.prisma` is untouched and there is no schema-push task in this plan.

**Fails closed (D-16), and that is the requirement, not polish.** If `GRAPH_SERVICE_URL` is unset, or the service is down, slow, non-ok, or returns a body that fails validation, `fetchGraphPreferences` returns null and the agent behaves exactly as Phase 7 left it. The 2-second abort signal and the try/catch are the mitigation for T-09-07.

**Additive only (D-18, D-19).** The `lib/agent/**` edit never restructures Phase 5/7 code: two added lines and one changed expression at a single call site. `lib/slack/**`, `lib/calendar/**`, `app/**`, `components/**`, `lib/ai/**`, `lib/agent/tasks/**`, `trigger.config.ts`, `prisma/schema.prisma`, `package.json` and `bun.lock` are not touched. No new npm dependency: native `fetch` and `AbortSignal.timeout` only.

**The `group_id` decision, stated once so both ends agree.** The partition key is **the Slack user id of the message author**, which in this demo is **demo user A** — the only user with Google consent and the person whose calendar the proposal targets. Why the author and not the organizer: `organizer_user_id` is null at proposal creation time and stays null until Phase 4's conditional claim (Phase 5 plan 05-01, propose step f), so the organizer is literally not knowable at the call site, while the author id is already in scope as the incoming `SlackMessage.userId`. The demo therefore has A post the scheduling message, and the demo `curl` POSTs that same Slack id as `user_id`. Task 2 captures the id once into a shell variable and uses it for the curl, the Browser `:param`, and nothing else.

**Budget, deadline, abandon (D-02, D-03, D-04).** This plan runs only if 09-01's round trip went green inside its 30-minute clock. Demo-ready deadline is **14:40 HKT**; branch `gsd/phase-9-s1-graphiti`, labelled [throwaway]. If the before/after change cannot be shown, cut S1: nothing merges to `main`, and the outcome is recorded in the SUMMARY for the Phase 11 README.

**Reversibility:** everything here is reversible — a throwaway branch, two new files and one two-line call-site edit. No `checkpoint:decision` is inserted.

**No tests of any kind (D-20).** Every check below is a hand check under a minute.

Output: `graph/queries.cypher`, `lib/agent/graph-preferences.ts`, one additive `lib/agent/**` call site, and a recorded before/after observation.
</objective>
