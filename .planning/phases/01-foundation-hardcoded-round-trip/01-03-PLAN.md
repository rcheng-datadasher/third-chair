<objective>
Prove the whole product loop on hardcoded data, and fix every cross-track seam so Waves A and B can start in parallel.

**User story (MVP mode):** **As a** demo watcher, **I want to** see an ordinary Slack mention turn into an approval card and, after one click, into a confirmed chip on that same message, **so that** the approval-gate thesis is visible before any model or calendar code exists.

Purpose: SLK-07 is the phase's exit criterion and the project's whole shape in miniature. Proving it here, centrally, means the Slack and Calendar tracks build on a harness that is already known to work — a wiring bug found later would block both tracks, not one. FND-09's stubs are what make those merges mechanical.

Output: the hardcoded round trip running through real Bolt, real Postgres and real Slack, plus the full stub set for every seam a parallel track consumes.

This plan carries the phase's tracer (Task 1): one mention → one dispatch → one agent run → one DB write → one card → one click → one DB update → one `chat.update`. Every layer the milestone will ever touch, wired once, on one path.
</objective>

Wire one mention through every layer, end to end, and stop there. No second entry point, no batching, no extra listeners.

Types first (D-07). `types/slack.ts` exports the runtime-free interface `SlackMessage` with `teamId`, `channelId`, `ts`, optional `threadTs`, `userId`, `text`. `types/agent.ts` exports `RunAgentInput` (wrapping one `SlackMessage`), `RunAgentResult` (`proposalId` and `decisionId`, each nullable), plus `ExtractedIntent` and `ConflictSlot` exactly as the interface table spells them. Database entity types are imported from the generated Prisma client and are never re-declared here.

`lib/agent/dedupe.ts` is real, not a stub: `computeDedupeKey(teamId, channelId, threadOrMessageTs, normalizedIntent)` returns a lowercase hex sha256 digest of those four parts joined with a stable separator, using the standard library hash — no dependency. It is a pure function with no I/O.

`lib/slack/client.ts` exports a module-scope `slackClient` built from the bot token read through `config.slack`, mirroring the `lib/db.ts` singleton pattern — one client per process, never constructed inside a listener.

`lib/slack/blocks.ts` exports `buildApprovalBlocks(p)` and `buildConfirmedBlocks(p)`. The approval blocks are the minimal hardcoded card from the research example: one section with the proposal title, and one actions block holding a single primary button with action id `approve_proposal` and `value` set to the proposal id. The action-id convention `<verb>_proposal` and the id-in-value convention are fixed here for Phases 2, 4 and 7 (D-03). Only the approve control exists in Phase 1 — its counterpart button is Phase 2's SLK-05. The confirmed blocks are the same section plus a static confirmed status chip and no actions block. Card copy and layout are throwaway; Phase 2 replaces both builders.

`lib/slack/post-proposal-card.ts` exports `postProposalCard(proposal)` returning the posted `{ channel, ts }`. It posts through `slackClient` with `blocks` from `buildApprovalBlocks` and a top-level `text` fallback set to the proposal title — the Slack API requires that fallback alongside blocks for notification previews.

`lib/slack/update-proposal-card.ts` exports `updateProposalCard(channel, ts, proposal)` — three arguments, and it builds both the `text` fallback and the status blocks internally from `buildConfirmedBlocks`. It edits the existing message in place; it never posts a new one.

`lib/agent/graph.ts` exports `runAgent(input)`. Its Phase 1 body is hardcoded and contains no model call and no calendar call: compute a dedupe key from the real mention `ts` (so every mention yields a fresh row), upsert a `Proposal` on that key with a hardcoded title, a hardcoded start/end, tz `Asia/Hong_Kong`, status `pending` and a hardcoded confidence, attach the mentioning user as a `Participant`, then call `postProposalCard` and write the returned channel and ts back onto the row's `card_channel` and `card_ts` columns. Return a `RunAgentResult` carrying the new proposal id. Phase 5 replaces this body with the real compiled graph; the signature does not change.

`lib/agent/dispatch.ts` exports `dispatchAgentRun(input)` whose entire Phase 1 body awaits `runAgent` inline (D-04). No transport branching, no background-job wrapper, and no `trigger.config.ts` — Phase 4 owns all three and must add the Prisma build extension anyway.

`lib/slack/actions/approve-proposal.ts` exports `handleApproveProposal`, copied from the research example: acknowledge the click as the very first awaited statement, then narrow the payload with the `BlockButtonAction` cast the research names, read the proposal id from the button's own value, return quietly when the value is absent, look the row up through the shared client and return quietly when no row comes back, set `status` to `confirmed`, then call `updateProposalCard` with the `card_channel` and `card_ts` read off that row — never the identifiers carried in the click payload, which drift (D-02, and the anti-pattern is named explicitly in the research). Guard for a row whose stored card identifiers are still null and log rather than throw. Nothing in this handler may throw: Slack must not see an error from it.

`lib/slack/bolt.ts` is the process entry and holds registration only, with every handler body in its own module (this file is a named overlap for Phases 2, 4, 5 and 7 — they append registrations, they do not restructure). It constructs the Bolt app in Socket Mode from `config.slack`, registers one event listener for `app_mention` that builds a `SlackMessage` from the payload and awaits `dispatchAgentRun`, registers the `approve_proposal` action against `handleApproveProposal`, starts the app, and logs the exact line `bolt: socket mode connected` once started. Phase 1 registers no watched-channel listener — Phase 2 adds it, calling this same dispatch function (D-01). The `app_mention` trigger is deliberate: its scope is already installed, and the bot's own card cannot retrigger it, so there is no feedback loop.

TSDoc on every exported function per `CLAUDE.md`, kebab-case filenames, named exports, no `any` outside the documented Bolt payload cast.
