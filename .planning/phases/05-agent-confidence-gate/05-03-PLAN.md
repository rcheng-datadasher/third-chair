## Cross-phase additive contract changes

1. **New action id `edit_approve_proposal`** joins Phase 1 D-03's `<verb>_proposal` convention; button `value` is the proposal id, unchanged. Phase 7's conflict card adds its own id the same way.
2. **First `app.view` registration in the repo.** `lib/slack/bolt.ts` stays registration-only (Phase 2 D-17); Phase 7 appends beside these two lines.
3. **`postEditApproveCard(proposal)` deliberately mirrors `postProposalCard`'s signature** so `proposeNode` selects a poster by band. Phase 7's conflict card should add a third function with the same signature rather than branching inside a poster.
4. **`lib/slack/blocks.ts` gains three exports.** `buildApprovalBlocks` is *consumed* by `buildEditApproveBlocks` (actions row swapped), so any later change to the card's field set lands in both variants automatically.
5. **`updateProposalCard(channel, ts, proposal)` is consumed unchanged** for the post-submission re-render. This plan assumes its `pending` branch renders the approve/reject card; see Flagged assumptions for the fallback if it does not.
6. **Phase 4's `lib/slack/approve.ts` is neither called nor edited here.** The edit path ends at a corrected `pending` Proposal plus an approvable card; the calendar write stays behind the Approve click. If a later phase needs approval logic inline, it imports `approveProposal(id)` — it never re-implements it.
7. No Prisma schema change, no new package, no change to `runAgent`'s signature.
