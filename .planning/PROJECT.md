# AI Secretary

## What This Is

A Slack agent that reads ordinary conversation in a watched channel, decides on its own whether a message is an action item, and turns scheduling intents into **Proposals**. A proposal is a Block Kit approval card in Slack plus a row in a Next.js dashboard. Nothing is written to Google Calendar until the user approves. When a request clashes with the calendar, the agent proposes concrete alternative slots and says why. Built solo at the AI Tinkerers "Agents, Everywhere: Beyond The Chatbox" hackathon (Hong Kong, Sat 12 Sep 2026) and documented as a real open-source project.

## Core Value

**Unprompted intent detection with an approval gate:** an ordinary Slack message ("Let's have a talk next Friday at 11am") becomes an approvable proposal and, after one click, a real Google Calendar event with a Meet link. Nobody invokes the agent, and nothing reaches the calendar without approval.

### Active

**Demo path (must work on stage). User A has connected Slack and granted Google Calendar consent:**

- [ ] B posts an ordinary message to A in the watched channel: "Let's have a talk next Friday at 11am."
- [ ] The agent classifies actionability. Non-actionable chatter is ignored silently, and the ignore is recorded as a `Decision` and visible in the dashboard.
- [ ] For an actionable message it extracts a structured intent (title, resolved ISO start, duration, participants, confidence) and creates one **Proposal**, surfaced as a Block Kit approval card in Slack and as a row in the dashboard action-item list.
- [ ] Every approval card carries **Approve and Reject** buttons; a decision replaces the buttons in place with a status chip, so a second click cannot re-fire.
- [ ] A approves from the Slack card. The agent creates the event on A's Google Calendar with a Meet link, invites B by the email on B's Slack profile, and updates the same Slack message in place (`chat.update`) to a confirmed state with the event link.
- [ ] Later, B asks A for 10:30 the same day. The agent detects the conflict and **proposes two concrete alternative slots, each with a one-line stated reason**, rendered as buttons on the card. This is the headline moment. (The source doc used a third user C; only two Slack users exist, so B makes the second ask.)

**Two AI features that must both land:**

- [ ] **Confidence gate / should-I-act** (~20 min, sequenced first): `is_actionable` + `confidence` on the extraction schema. High confidence posts the approval card. Medium posts a card that opens the edit modal first. Low stays silent and is written to `Decision`. Precision decides whether the product is usable, not cost.
- [ ] **Conflict-aware counter-proposal** (~45 min): on a clash, busy blocks plus known preferences go to one extra `MODEL_SMART` call that returns two alternative slots, each with a one-line human reason, rendered as buttons.

### Runtime processes (who owns what)

- **Bolt process** (`@slack/bolt`, Node, Socket Mode, its own process): holds the WebSocket, receives messages (allowlisted channel), `app_mention`, message shortcuts, slash commands, `block_actions`, modal submissions; handles the 3-second ack; routes by type and callback id; uses `app.client` for `chat.postMessage`, `chat.update`, `views.open`, `users.info`. - **Next.js app** (App Router, TS): dashboard, action-item queue, `Decision` log, CopilotKit surface (S2). Request-scoped; no Slack connection.
- **Trigger.dev tasks**: invoke the LangGraph agent, retries, idempotency keys, anything slow or flaky off the Slack handler, and expiry sweeps that re-trigger the agent on stale action items. Trigger.dev calls LangGraph; LangGraph never schedules itself.
- **Postgres** (Docker locally). Consumers: Next.js, Bolt, Trigger.dev.
- **Graphiti FastAPI service** (S1 only, Python, separate repo): `POST /episodes`, `GET /preferences?user_id=`, optionally `GET /graph?user_id=`. Called from Trigger.dev. Neo4j behind the `graph` compose profile.

### Agent design

- **Graph path (≤5 nodes):** extract → classify actionability → resolve time → check conflicts → propose. If a node isn't on the path from a Slack message to a proposal, it doesn't exist tomorrow.
- **Explicit fallback:** if the graph is still fighting back at the first merge window after extraction lands, rip it out and call the plain node functions in sequence (a ten-minute change). The decision time is fixed in the roadmap.
- **Approval: re-derive, don't resume.** The agent run ends when the proposal is created (writes `Proposal`, posts card, finishes). The Approve handler is ordinary backend code: read row → re-check calendar as it is now → create event. Expiry: stamp action items; on expiry re-invoke the same agent with the intent prefilled and fresh context and write a new record. (README gets one line on the narrow case where `interrupt()` fits: a seconds-long pause that continues reasoning.)
- **Detection is per-message for the demo, batch-first in the documented design.** Signature `extractIntents(messages: SlackMessage[], ctx)`; the per-message path passes an array of one; messages are rendered as numbered lines and the model returns `message_index` per intent, mapped back to a Slack `ts`.
- **README batch-first reasoning:** a message is ~30 tokens vs a ~700-token system prompt, so batching a window amortizes the prompt for ~20× savings. Regex/keyword pre-filtering can't be the primary filter: it fails on "same time as last week", "after standup", typos, abbreviations and Cantonese-English code-switching, and its misses are silent and untunable. Production: a cheap local router for time-urgent messages only (poor recall allowed), a per-channel batch sweep over a bounded window as the workhorse, full extraction + conflict reasoning on candidates only; `dedupe_key` absorbs overlapping windows.
- **One Proposal per intent:** `dedupe_key = sha256(team_id + channel_id + (thread_ts ?? message_ts) + normalized_intent)`, where `normalized_intent` = type + ISO start rounded to 5-minute buckets + sorted participant set. Per-user `ActionItem` rows are views of the Proposal.
- **Exactly one organizer writes to Calendar:** default is the addressee; tiebreak is first approver wins via `UPDATE "Proposal" SET organizer_user_id = $me WHERE id = $p AND organizer_user_id IS NULL RETURNING id`. No row back is a UI state ("Ada already scheduled this"), not an error.
- **Calendar idempotency:** client-generated event `id` derived from the proposal id; on HTTP 409 fall back to `events.get` and treat it as success.
- **Conflict detection:** `freebusy.query` on the organizer's calendar unioned with pending Proposals in the DB.
